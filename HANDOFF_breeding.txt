1. ЦЕЛЬ И РЕШЕНИЯ ВЛАДЕЛЬЦА
--------------------------------------------------------------------
ЦЕЛЬ: игрок сводит двух совместимых покемонов в ПИТОМНИКЕ -> появляется ЯЙЦО ->
через ИНКУБАЦИЮ (таймер) яйцо вылупляется в потомка.

РЕШЕНИЯ ВЛАДЕЛЬЦА (2026-07-21):
  - ВИД потомка = БАЗОВАЯ ФОРМА линии МАТЕРИ (спуск по evolves_from_id до
    начальной формы; из Charizard-мамы вылупляется Charmander).
  - ЯЙЦО + ИНКУБАЦИЯ ПО ТАЙМЕРУ (не шаги/бои). Время и уровень вылупления —
    КОНСТАНТЫ в коде (старт: инкубация 1 час, уровень вылупления 1).
  - НАСЛЕДОВАНИЕ — ТОЛЬКО IV: для каждого из 6 генов потомок берёт МАКСИМУМ гена
    двух родителей; затем с шансом 30% этот ген +1 (кап 31). Пример: род.1 HP=20,
    род.2 HP=25 -> яйцо HP=25, с шансом 30% -> 26. Натура/буква/пол — СЛУЧАЙНЫЕ
    (наследуется только IV).
  - ПАРЫ (совместимость). ВО ВСЕХ случаях требуется ОДИНАКОВЫЙ ВИД (pokemon_id
    равны) И одинаковая БУКВА привлекательности. Потомок = базовая форма этого вида.
      * ОБЫЧНАЯ (M/F): один 'M' + один 'F', ОДИН вид, одна БУКВА.
      * БЕСПОЛЫЕ (N/N) через предмет АМУРИТ: оба 'N', ОДИН вид, одна БУКВА, И на
        ОБОИХ надет предмет «Амурит» (held-предмет, как STAB из [6]).
      * Иначе — разводить НЕЛЬЗЯ (разные виды, разные буквы, один N без пары/без
        Амурита, оба M и т.п.).
  Амурит НЕ расходуется (это надетый предмет, остаётся на покемоне).

НЕ ДЕЛАЕМ сейчас: egg-мувы (особые ходы от родителей), наследование натуры/предметы
типа Эверстоуна, шаговую инкубацию, случайные виды-«бэби» (Pichu и т.п. вне схемы),
кулдауны сверх «одно яйцо на пару за раз». Наследуем ТОЛЬКО IV.

БД:

Бэкенд (Go):

    (случайная буква), тип UserPokemon{ID,PokemonID,Gender,Attractiveness} и
    CanBreed(a,b *UserPokemon) — ТЕКУЩАЯ ЗАГЛУШКА правила: одинаковая буква +
    противоположные полы M/F (бесполых отвергает). РАСШИРИТЬ под Амурит (см. §4).
  - utils/create_pokemon.go CreateUserPokemon(userID, pokemonID, level, iv [6]int,
    natureID, gender, geneBonus, happinessBonus, forceNursery) — ЕДИНАЯ точка

  - handlers/api/nursery.go: GetUserPokemonsForNursery (список питомника),
    TakeToTeamHandler, SendToNurseryHandler. Маршруты /api/nursery/* в routes.go.

3. СХЕМА БД (поток [13])
--------------------------------------------------------------------
Под бэкап pokemon.db.bak-before-breeding. Новая таблица — в срез database.go
(CREATE TABLE IF NOT EXISTS). Времена — TEXT ISO8601 или INTEGER unix (согласуй с
тем, как в проекте уже хранят created_at; user_pokemons.created_at уже есть — взять
тот же формат).

  CREATE TABLE IF NOT EXISTS eggs (
    id INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL,
    species_id INTEGER NOT NULL,        -- БАЗОВАЯ форма, которая вылупится
    iv_hp INTEGER, iv_attack INTEGER, iv_defense INTEGER,
    iv_speed INTEGER, iv_special_attack INTEGER, iv_special_defense INTEGER,
    parent1_id INTEGER, parent2_id INTEGER,  -- для отображения (необязательно в логике)
    created_at <как в user_pokemons>,
    hatch_at   <created_at + INCUBATION>,     -- когда можно вылупить
    FOREIGN KEY(user_id) REFERENCES users(id),
    FOREIGN KEY(species_id) REFERENCES pokemons(id)
  );

Предмет «Амурит»:
  - Завести айтем: category = held (id 9, как STAB), effect_type='breed_amurite'
    (по нему опознаём Амурит), image_url (можно временно любой значок).
    Через админку items ИЛИ python. Выдать тест-игроку 2 шт. (на пару бесполых).
  - НИКАКИХ новых колонок под Амурит не надо — опознаём по items.effect_type.

4. БЭКЕНД — ЛОГИКА (handlers/api/breeding.go, новый + db/gender.go)
--------------------------------------------------------------------
Константы-«ручки» вверху breeding.go:
  incubationDuration = 1 * time.Hour
  hatchLevel         = 1
  ivPlusChance       = 0.30   // шанс +1 к унаследованному гену
  ivCap              = 31

(4.1) РАСШИРИТЬ проверку совместимости. В db/gender.go добавить в UserPokemon поле
      HeldEffect string (effect_type надетого предмета, '' если нет) и HasAmurite
      bool ИЛИ передавать флаг Амурита отдельно. Новая функция (или расширить
      CanBreed — но у неё нет вида/предмета; лучше НОВАЯ):
        BreedCompat(a, b *UserPokemon) (ok bool, reason string)
      Правила:
        - a.ID != b.ID; оба существуют;
        - ОДИНАКОВЫЙ ВИД: a.PokemonID == b.PokemonID — ИНАЧЕ reason «разные виды»;
        - буквы равны (a.Attractiveness == b.Attractiveness) — ИНАЧЕ reason;
        - если оба 'N': у ОБОИХ надет Амурит (HeldEffect=='breed_amurite') — иначе
          reason «нужен Амурит на обоих»;
        - иначе один 'M' + один 'F' (не 'N') — ок;
        - любой другой случай (один N без пары-N+Амурит, оба M и т.п.) — нельзя.
      Старую CanBreed можно оставить (обратная совместимость) или свести к BreedCompat.

(4.2) БАЗОВАЯ ФОРМА. Хелпер baseFormOf(pokemonID) int: идти по evolves_from_id
      вверх по линии, пока не NULL (ЗАЩИТА от цикла: максимум ~5 шагов/по посещённым).
      Вид пары ОДИН (a.PokemonID==b.PokemonID) -> потомок = baseFormOf(этого вида).

(4.3) IV ПОТОМКА. Для каждого из 6 генов: iv = max(p1.iv, p2.iv); если
      rand.Float64() < ivPlusChance и iv < ivCap: iv++. Порядок HP,Atk,Def,Spd,
      SpAtk,SpDef (как везде). Читать iv_* родителей из user_pokemons.

(4.4) ЭНДПОИНТЫ (routes.go, рядом с /api/nursery/*):
  POST /api/battle... нет. Питомник:
  - POST /api/nursery/breed  {parent1_id, parent2_id}:
      auth; оба покемона принадлежат userID И оба В ПИТОМНИКЕ (position 0/NULL);
      собрать UserPokemon обоих (+ HeldEffect из join items по held_item_id);
      BreedCompat -> при неуспехе 400 с reason;
      определить species_id = baseFormOf(матери/общего вида);
      посчитать IV потомка (4.3);
      (guard) запретить, если для ЭТОЙ пары уже есть незавершённое яйцо;
      INSERT eggs (created_at=now, hatch_at=now+incubationDuration, iv_*, species_id,
      parent1_id, parent2_id); вернуть JSON яйца (id, вид, картинка, hatch_at).
  - GET /api/nursery/eggs:
      список яиц игрока: id, species_id, имя/картинка базовой формы, hatch_at,
      ready (now>=hatch_at), remaining_seconds. ORDER BY created_at.
  - POST /api/nursery/hatch  {egg_id}:
      auth; яйцо принадлежит userID; НЕ раньше hatch_at (иначе 400 «ещё не готово»);
      natureID = случайная натура (как в wild.go: SELECT ... FROM natures ORDER BY
      RANDOM() LIMIT 1); gender = db.RollGender(species_id);
      newID = utils.CreateUserPokemon(userID, species_id, hatchLevel, storedIV,
      natureID, gender, 0, 0, false);  // attractiveness роллится внутри (случайная)
      DELETE eggs WHERE id=egg_id; вернуть нового покемона (id, имя, уровень).
  Всё под теми же auth/ошибками, что прочие nursery-хендлеры.

6. ТЕСТ-ДАННЫЕ И ПРОВЕРКА (DoD)
--------------------------------------------------------------------
Тест-данные (python/админка, под бэкап):
  - Пара M/F: два покемона ОДНОГО ВИДА в питомнике тест-игрока с ОДИНАКОВОЙ буквой
    и полами M и F (проверить, что потомок = базовая форма этого вида). Плюс отдельно
    пара РАЗНЫХ видов — убедиться, что развести НЕЛЬЗЯ. Проставить заметные iv_*
    (напр. род.1 HP=20, род.2 HP=25) для проверки правила max+30%.
  - Пара N/N: два бесполых ОДНОГО вида, одинаковая буква; создать предмет Амурит
    (effect_type='breed_amurite', held-категория) и надеть на ОБОИХ (held_item_id).
  - Для быстрой проверки таймера можно ВРЕМЕННО выставить incubationDuration
    маленьким (напр. 10 сек) — вернуть 1 час перед сдачей.

DoD (осн. ПК, обязателен ЖИВОЙ прогон — билд+vet это НЕ «готово»):
  [ ] go build -o server.exe ./server + go vet ./... — зелёные;
  [ ] M/F ОДНОГО вида с одной буквой -> «Развести» -> ЯЙЦО базовой формы вида;
  [ ] РАЗНЫЕ виды / разные буквы / оба M / один N без Амурита -> развести НЕЛЬЗЯ
      (внятный отказ);
  [ ] N/N одного вида + одна буква + Амурит на ОБОИХ -> яйцо; без Амурита -> отказ;
  [ ] яйцо нельзя вылупить до срока; после hatch_at -> «Вылупить» создаёт потомка
      в питомнике через CreateUserPokemon (атаки инициализированы, статы верные);
  [ ] IV потомка = МАКСИМУМ родителей по каждому гену, иногда +1 (кап 31); натура/
      буква/пол — случайные (пол по ратио вида);
  [ ] уровень вылупившегося = hatchLevel; вид = БАЗОВАЯ форма линии матери;
  [ ] таймер на клиенте тикает; после готовности кнопка активна;
  [ ] существующий питомник/команда/ловля/held-предметы НЕ сломаны.

7. ГРАБЛИ / РИСКИ
--------------------------------------------------------------------
  - ЕДИНАЯ ТОЧКА: потомок ТОЛЬКО через utils.CreateUserPokemon (не дублировать
    роллы статов/attractiveness). Пол передаём (RollGender по виду потомка),
    натуру роллим (случайную), IV — вычисленные.
  - Наследуем ТОЛЬКО IV (макс+30%/кап31). Букву НЕ наследуем (случайная), хотя у
    пары она совпадает — так решил владелец.
  - baseFormOf: защита от цикла в данных (счётчик шагов), иначе вечный цикл.
  - Амурит опознаём по items.effect_type='breed_amurite' у НАДЕТОГО предмета обоих
    (join user_pokemons.held_item_id -> items). Амурит НЕ расходуется.
  - IV-шкала 0..31 (кап как в CreateUserPokemon). NB (не в этой задаче): дикий
    генератор wild.go катит IV 0..5 — пойманные родители дадут слабых потомков;
    отдельный баг, здесь НЕ трогаем.
  - Оба родителя — В ПИТОМНИКЕ и принадлежат игроку; не давать разводить чужих/из
    активной команды (по вкусу — но проще требовать питомник).
  - Время: хранить hatch_at абсолютным; готовность = now>=hatch_at (серверное
    время — источник правды, клиентский таймер только показывает).
  - Go на RDP НЕТ: правки файлов + БД (python, utf-8, bash-героку, бэкап).
    Отчёт -> TEST_breeding.txt, чек-лист §6.
