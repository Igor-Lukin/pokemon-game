1. ЦЕЛЬ И ГРАНИЦЫ
--------------------------------------------------------------------
ЦЕЛЬ: показывать ДРУГИХ игроков, которые СЕЙЧАС онлайн и на ТОЙ ЖЕ локации —
панелью ПРАВЕЕ ЧАТА. У каждого: ник + иконка; по нажатию иконки — контекст-меню
(выпадающий список):
  - «Тренеркарта» — ПОКА НЕ РАБОТАЕТ (пункт-заглушка, задизейблен/тост «скоро»);
  - «Вызвать на бой» — РЕАЛИЗОВАТЬ ФЛОУ ВЫЗОВА (пригласить -> уведомить -> принять/
    отклонить). САМ PvP-БОЙ в этой задаче НЕ делаем — на «принять» дергаем ЗАГЛУШКУ
    startPvpBattle (стык для Части B).

ТРАНСПОРТ: HTTP-ПОЛЛИНГ (решение владельца; вебсокетов в проекте по факту нет —
чат-ws это нерабочая клиентская заглушка). Спроектировать так, чтобы presence и
вызовы жили СЕРВЕРНЫМ состоянием, а клиент их ОПРАШИВАЛ — тогда позже поверх можно
навесить ws-пуш БЕЗ смены модели данных (эндпоинты/формы ответов оставить стабильными).

НЕ ДЕЛАЕМ здесь (Часть B / позже): сам PvP-бой (общая боевая сессия двух людей,
синхронизация ходов); рабочую «Тренеркарту» из меню; вебсокеты; чат (он отдельно
сломан — см. §2, не наша задача).

3. СЕРВЕРНОЕ СОСТОЯНИЕ (эфемерное, под будущий ws)
--------------------------------------------------------------------
Вызовы — эфемерные, храним В ПАМЯТИ под мьютексом (как battleSessions), с TTL.
Таблицы БД НЕ обязательны (можно без миграций). Модель:
  challenge{ challengerID, targetID, createdAt, status: pending|accepted|declined }
  - хранилище: map по targetID -> входящие вызовы (или по паре id); mutex.
  - TTL: вызов живёт ~45с (challengeTTL, константа), потом протухает и убирается.
  - Гарды: нельзя вызвать себя; цель должна быть онлайн И на той же локации; один
    активный исходящий вызов на пару (не спамить дублями).
Presence НЕ храним отдельно — считаем из users.last_seen+location_id на лету.

4. БЭКЕНД — ЭНДПОИНТЫ (handlers/api/online.go, новый; routes.go)
--------------------------------------------------------------------
Все JSON, auth по сессии. Константы-«ручки» вверху: onlineWindow=5*time.Minute,
challengeTTL=45*time.Second.

(4.1) GET /api/location/players  — кто онлайн на МОЕЙ локации (кроме меня):
      SELECT u.id, u.username FROM users u
      WHERE u.location_id = (моя локация) AND u.id != me
        AND u.last_seen >= (now-onlineWindow)   -- то же правило, что online в [7]
      ORDER BY u.username.
      Ответ: [{user_id, username}]. (avatar/иконку — по желанию; ник обязателен.)
      Моя локация — из users.location_id по userID.

(4.2) POST /api/challenge  {target_user_id}  — отправить вызов:
      гарды §3 (не себя; цель онлайн и на той же локации; нет дубля). Создать
      pending-вызов в памяти. Ответ ok (или 400 с причиной: «игрок не онлайн/ушёл
      с локации/уже вызван»).

(4.3) GET /api/challenge/incoming  — ВХОДЯЩИЕ вызовы мне (поллит цель):
      вернуть pending-вызовы, где target==me, с {challenger_id, challenger_name}.
      Протухшие (>TTL) не отдавать (и чистить).

(4.4) POST /api/challenge/respond  {challenger_id, accept}  — ответ цели:
      accept=false -> пометить declined/удалить.
      accept=true  -> пометить accepted; ДЁРНУТЬ ЗАГЛУШКУ startPvpBattle(challengerID,
        targetID) (Часть B заменит на реальный старт PvP). В этой задаче startPvpBattle
        — СТАБ: залогировать + пометить вызов accepted (чтобы обе стороны увидели по
        поллингу). Ответ ok.

(4.5) GET /api/challenge/outgoing  — СТАТУС моего исходящего вызова (поллит
      инициатор): {status: none|pending|accepted|declined, target_name}. По accepted/
      declined инициатор реагирует (accepted -> заглушка «бой скоро»; declined ->
      «отклонил»); после показа — вызов можно очистить.
Маршруты в routes.go рядом с прочими /api/*.
