1. ЗАДАЧА И ГРАНИЦЫ
--------------------------------------------------------------------
Способности — пассивные умения в БОЮ, у каждого покемона РОВНО ОДНА из доступных
его виду. Сейчас в игре способности есть как ДАННЫЕ (таблицы abilities/
pokemon_abilities) и админка, но: (а) у экземпляра способность НЕ закреплена
(в команде показывается «первая не-скрытая» вида на лету), (б) в бою способности
НИЧЕГО не делают, (в) нет слотов/скрытых/ремапа при эволюции.

ЭТА ЗАДАЧА = КАРКАС (инфраструктура), чтобы потом (в ОТДЕЛЬНОМ чате) агент лишь
ДОБАВЛЯЛ конкретные эффекты «по полкам». Реализуем:
  - слоты способностей у вида (базовая X / базовая Y / скрытая);
  - закрепление способности за ЭКЗЕМПЛЯРОМ (user_pokemons) + случайный выбор
    базовой при создании (единая точка) + бэкфилл существующих;
  - СОХРАНЕНИЕ СЛОТА при эволюции (ремап способности по слоту, спец-случай 1->2);
  - загрузку способности в бой (BattlePokemon.AbilityKey) + пустой диспетчер
    эффектов с РАЗМЕЧЕННЫМИ хук-точками (эффектов пока НЕ пишем);
  - админку: слот у pokemon_abilities + effect_key у abilities.

НЕ ДЕЛАЕМ в этой задаче (следующий чат): конкретные ЭФФЕКТЫ способностей; способ
ПОЛУЧЕНИЯ СКРЫТОЙ способности игроком (пока только через админ/данные). Правило
назначения при создании = СЛУЧАЙНАЯ БАЗОВАЯ (владелец подтвердил в дизайне).

2. ДИЗАЙН ВЛАДЕЛЬЦА (модель способностей — из чего исходим)
--------------------------------------------------------------------
  - У вида 1..3 слота: БАЗОВАЯ X (слот 1, есть всегда), БАЗОВАЯ Y (слот 2, опц.),
    СКРЫТАЯ (опц.). Одна и та же способность может быть базовой у одного вида и
    скрытой у другого (per-строка is_hidden).
  - При поимке/выдаче/вылуплении — СЛУЧАЙНО одна из БАЗОВЫХ (X или Y). Скрытая при
    обычном создании НЕ выпадает.
  - Экземпляр ПОМНИТ свой слот. При эволюции слот СОХРАНЯЕТСЯ, способность берётся
    из того же слота нового вида:
      * #048 «Фасеточные глаза» (слот X) -> #049 «Чешуекрылое» (слот X);
      * #048 «Особое зрение» (слот Y) -> #049 «Особое зрение» (слот Y);
      * скрытая -> скрытая аналогично.
    (Имена в примерах — игровые/условные; ССЫЛАЕМСЯ НА ВИДЫ ПО id = нац. номеру:
     #048/#049 -> pokemons.id 48/49; #349/#350 -> 349/350.)
  - СПЕЦ-СЛУЧАЙ: если у формы ДО эволюции базовых было МЕНЬШЕ, чем ПОСЛЕ (напр. было
    1, стало 2) — базовая после эволюции выбирается СЛУЧАЙНО из базовых нового вида
    (#349 один базовый -> #350 два базовых: «Перламутровый доспех» ЛИБО «Конкуренция»).
  Правило ремапа, покрывающее оба примера (см. §5): если ЧИСЛО базовых у пре- и
  пост-формы РАВНО — сохраняем ТОТ ЖЕ слот (позиционно); если различается — СЛУЧАЙНО
  среди базовых нового вида.

4. СХЕМА БД (каркас; бэкап обязателен)
--------------------------------------------------------------------
[СВЕРКА] Миграции — по КОНВЕНЦИИ ПРОЕКТА: просто DB.Exec("ALTER TABLE … ADD COLUMN …")
в существующем блоке миграций db/database.go (~строка 409, там же где gender/happiness/
avatar_data). Ошибка «duplicate column» игнорируется — PRAGMA-проверки НЕ нужны (в
проекте их нигде нет). Новые данные (миграция slot + бэкфилл) — тем же блоком, под бэкап
pokemon.db.bak-before-abilities.

(4.1) abilities: + effect_key TEXT
      Машиночитаемый ключ для диспетчера в коде (напр. 'blaze','intimidate'). Может
      быть NULL/'' пока эффект не реализован. Заполняется позже (в другом чате).

(4.2) pokemon_abilities: + slot INTEGER
      Семантика: 1 = базовая X, 2 = базовая Y, 3 = СКРЫТАЯ. Мигрировать существующие
      строки: is_hidden=1 -> slot=3; is_hidden=0 -> раздать slot 1,2 по порядку
      (ORDER BY ability_id/rowid внутри вида: первая -> 1, вторая -> 2). is_hidden
      оставить (согласованно: hidden <=> slot=3).
      NB: у большинства видов будет 1 базовая (slot 1). Слот 2/3 — у кого есть.

(4.3) user_pokemons: + ability_id INTEGER, + ability_slot INTEGER
      ability_id — закреплённая способность экземпляра; ability_slot — её слот
      (1/2 базовая, 3 скрытая) для ремапа при эволюции. У видов без способностей —
      NULL/NULL (обрабатывать как «нет способности», не падать).

8. ТЕСТ-ДАННЫЕ И ПРОВЕРКА (DoD)
--------------------------------------------------------------------
Тест-данные (под бэкап): убедиться, что у пары эволюционных видов заданы слоты по
образцу дизайна (напр. #048->#049 с 2 базовыми в обоих + скрытая; #349->#350 с
1 базовой у #349 и 2 у #350). Если данных нет — проставить через админку/python.
Демонстрация диспетчера: ОДНА безвредная тест-ветка (напр. effect_key='logtest' ->
abilityOnSwitchIn пишет в лог «сработала способность X») — чтобы доказать, что
способность экземпляра доезжает до боя. Перед сдачей тест-ветку можно оставить
(безвредна) или убрать.

DoD (осн. ПК, ЖИВОЙ прогон обязателен):
  [ ] go build + go vet — зелёные;
  [ ] у нового пойманного/вылупленного покемона проставлена СЛУЧАЙНАЯ БАЗОВАЯ
      способность (ability_id/ability_slot заполнены); в команде видно её имя;
  [ ] бэкфилл: у ранее существующих покемонов способность проставлена;
  [ ] эволюция сохраняет СЛОТ: слот1->слот1, слот2->слот2, скрытая->скрытая
      (проверить на #048->#049); при 1->2 базовых (#349->#350) — способность
      случайная из двух базовых новой формы;
  [ ] способность экземпляра доезжает до боя (тест-ветка логирует при выходе);
  [ ] РЕГРЕССИЯ: с ПУСТЫМИ хуками урон/статусы/бой/ловля/эволюция — БЕЗ изменений
      (пустые хуки нейтральны);
  [ ] админка: effect_key у способности сохраняется; slot у вид-способности задаётся;
  [ ] wild/trainer-покемоны в бою получают способность (транзиентно) — видно в логе.
