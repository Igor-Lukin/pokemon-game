================================================================
ЗАДАНИЕ НА ТЕСТ: Фаза 0 системы карточек статусов (pokemon-game)
================================================================
Кому: агенту-разработчику на основном ПК (есть Go, есть репозиторий).
Что сделано: рефакторинг, который НЕ должен менять поведение боя.
Твоя задача: собрать, проверить, что поведение прежнее, и оставить
комментарий-вердикт внизу этого файла (раздел "ОТЧЁТ").

----------------------------------------------------------------
1. ЧТО ИЗМЕНИЛОСЬ (Фаза 0)
----------------------------------------------------------------
Цель: собрать поведение каждого статуса в одну "карточку" (StatusDef)
в реестре, вместо разбросанных по battle.go проверок StatusID.
Поведение боя должно остаться БАЙТ-В-БАЙТ прежним (тексты в логах,
цифры урона, формулы). Это чисто организация кода.

Новый файл:
  server/handlers/api/status_registry.go
    - тип StatusDef (8 "граф": Name/TickWord/ImmuneTypes/Duration/
      OnTurn/StatMult/CanAct/MoveFilter/Custom)
    - var statusRegistry: карточки статусов 2,3,4,5,6,7
    - func statMultiplier(statusID, statIdx) float64
    - Condition + func conditionMet(...)  — ЗАГОТОВКА для Фазы 2,
      намеренно НИГДЕ не вызывается (поведение не меняет).

Правки в server/handlers/api/battle.go (3 точки):
  (а) processPreTurnStatus: три отдельных блока урона по ходам
      (ожог 1/16, отравление 1/8, сильное отравление нарастающее)
      заменены ОДНИМ блоком, берущим урон из карточки (def.OnTurn).
  (б) calculateDamage: строка про ожог `if StatusID==3 { a=a/2 }`
      заменена на `a = int(float64(a) * statMultiplier(StatusID,1))`.
  (в) effectiveSpeed: `if StatusID==2 { s=s/2 }`
      заменена на `s = int(float64(s) * statMultiplier(StatusID,3))`.

Прочие статусные механики (пропуск хода при параличе, разморозка,
сон, замешательство/confusion, флинч, семена, ловушка) НЕ трогались —
они переносятся в следующих фазах.

3. ПРОВЕРИТЬ, ЧТО ПОВЕДЕНИЕ ПРЕЖНЕЕ
----------------------------------------------------------------
Эталон (как должно работать, оно же было до правок):

  ОЖОГ (status_id=3):
    - каждый ход носитель теряет max(1, MaxHP/16);
    - лог: "<Имя> получает урон от ожога! -<N> HP";
    - физические атаки носителя бьют вдвое слабее (целочисленно a/2).
  ОТРАВЛЕНИЕ (6):
    - каждый ход max(1, MaxHP/8);
    - лог: "<Имя> получает урон от отравления! -<N> HP".
  СИЛЬНОЕ ОТРАВЛЕНИЕ (7):
    - урон нарастает: 1/16, 2/16, 3/16 ... (потолок 15/16), min 1;
    - счётчик p.PoisonTurns увеличивается на 1 каждый ход;
    - лог: "<Имя> получает урон от сильного отравления! -<N> HP".
  ПАРАЛИЧ (2):
    - эффективная скорость носителя = целочисленно Speed/2
      (ДО применения ступеней статов), затем ступени, затем min 1.
    - (шанс 25% пропустить ход — прежний код, не трогался.)

Способы проверки (любой из/оба):
  A) Прочитать диффы и подтвердить, что формулы/тексты идентичны
     (особенно: min-1, целочисленное деление, порядок в effectiveSpeed —
     множитель статуса ПЕРЕД множителем ступеней).
  B) Запустить сервер и провести бой:
       go run ./server   (или ./server.exe)
     затем нанести статусы и сверить урон/лог/скорость.
     Удобная тестовая атака: "Отростки" (id=9) — статусная, +Атака/+СпАтака.
     Для ожога/яда/паралича — любые атаки с соответствующим effect_status_id.

Крайние случаи, на которые обратить внимание:
  - MaxHP < 16: урон ожога должен быть 1 (min-1), не 0.
  - int(float64(a)*1.0) для НЕстатусных покемонов должно равняться a
    (никакого случайного округления вниз).
