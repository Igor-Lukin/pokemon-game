0. КАК ЧИТАТЬ ЭТОТ ФАЙЛ
--------------------------------------------------------------------
Это не код, а согласованный ПЛАН и решения. Реализации пока НЕТ —
код проекта в исходном рабочем состоянии. Первый шаг разработки —
"Фаза 0" (см. раздел 7). Владелец проекта не программист: объясняй
простым языком, показывай на его реальном коде, двигайся маленькими
проверяемыми шагами, не тащи лишнюю сложность.

--------------------------------------------------------------------
1. ПРОЕКТ / ТЕХНИКА
--------------------------------------------------------------------
pokemon-game: Go-бэкенд + SQLite + серверный HTML + админка.
- БД: ./database/pokemon.db (путь задан в server/db/database.go).
- Бинарь запускается из КОРНЯ проекта (использует ./database/... и
  ./server/templates/...).
- Сборка (на машине владельца, НЕ на RDP-сервере — там нет Go):
      go build -o server.exe ./server
- Бой целиком в server/handlers/api/battle.go (~1700 строк).
- Админка атак: server/handlers/admin/attacks.go +
  server/templates/admin/attack_form.html

--------------------------------------------------------------------
2. ЗАДАЧА
--------------------------------------------------------------------
У атак есть доп.эффекты: статусы (ожог, сон, паралич...), а также
УСЛОВНЫЕ эффекты. Эталонный пример — атака "Отростки" (Growth, id=9):
даёт Атака+1 и СпАтака+1, НО в СОЛНЕЧНУЮ погоду +2/+2.
Статусов будет ОЧЕНЬ много (см. раздел 4 — полный список из вики).

--------------------------------------------------------------------
3. ЧТО УЖЕ РЕШЕНО (важно — не повторять ошибку)
--------------------------------------------------------------------
ПРОБОВАЛИ и ОТКАТИЛИ: полностью data-driven движок, где эффекты атак
хранятся строками JSON в таблице attack_effects и настраиваются в
админке. Признано СЛИШКОМ СЛОЖНЫМ для этого проекта. НЕ ДЕЛАТЬ снова.
Причина: 44 механики почти все УНИКАЛЬНЫ и привязаны к одной атаке —
это "длинный хвост". Такой хвост в JSON не выразишь, он всё равно код.

СОГЛАСОВАННОЕ НАПРАВЛЕНИЕ: не "данные вместо кода", а "код, разложенный
по полкам". Две вещи, которые сейчас смешаны, надо разделить:

  (А) ПОВЕДЕНИЕ статуса (что "ожог" делает каждый ход) = КОД, неизбежно.
      Сейчас оно РАЗМАЗАНО по 5 местам battle.go на каждый статус.
      Решение — "реестр карточек": у каждого статуса одна КАРТОЧКА, где
      собрано всё его поведение. Движок боя тупой и общий, вся
      уникальность — в карточках. Это организация кода, НЕ админка, НЕ JSON.

  (Б) ПРИВЯЗКА атака->статус + УСЛОВИЕ (Отростки +2 в солнце) = тонкий
      слой данных: какой статус вешает атака, с каким шансом, при каком
      условии. В админке это простой выпадающий список + шанс + условие,
      без JSON-простыни.

  (В) УСЛОВИЯ (солнце? трава-иммунна? HP<33%? арена?) = один общий
      "помощник условий": функция-судья да/нет про состояние боя.
      Переиспользуется и иммунитетами, и условиями атак, и модификаторами
      арен. Пишется один раз.

--------------------------------------------------------------------
5. БЛАНК КАРТОЧКИ СТАТУСА ПОКЕМОНА (согласован) — 8 ГРАФ
--------------------------------------------------------------------
Один общий бланк на ВСЕ статусы. Пустые графы (nil) ничего не стоят.
Графа заводится только под ПОВТОРЯЮЩИЙСЯ приём; похожие одиночки
сливаются в одну обобщённую графу; настоящая экзотика — в "СвойКод".

  1. Имя             string              — текст в логе
  2. ИммунныТипы     []int               — типы, на которых не действует
  3. Длительность    int                 — сколько ходов живёт (0 = до лечения)
  4. КаждыйХод       func(p) int         — изменение HP за ход (- урон / + лечение)
  5. МножительСтата  map[стат]float64    — постоянные множители статов, пока висит
  6. МожетДействовать func(p) bool       — проверка "не пропускает ли ход"
  7. ФильтрАтак      func(p, атака) bool — какие атаки запрещены
  8. СвойКод         func(бой, p)        — заглушка для уникальной экзотики

Раскладка механик по графам:
  ИммунныТипы     : В огне, Отравлен, Парализован, Заморожен, Семена-пиявки
  Длительность    : Сон, Спутан, Ловушка, Насмешка, Овации, Скорбная песнь,
                    Запрет регена, Напуган, Заряд
  КаждыйХод        : В огне -1/16, Отравлен -1/8, Сильный яд (растёт),
                    Проклят -1/4, Кошмары -1/4, Семена -1/8, Ловушка -1/16,
                    Водный покров +1/16, Укоренение +1/16
  МножительСтата  : В огне (Атака x0.5), Парализован (Скорость x0.25)
  МожетДействовать : Парализован 25%, Сон, Заморожен, Спутан 50%+бьёт себя,
                    Напуган, Увлечён 50%
  ФильтрАтак      : Насмешка, Подстрекательство, Овации, Потеря памяти,
                    Запрет регена
  СвойКод          : Скорбная песнь, Заряд, Третий глаз/Обнаружение,
                    Концентрация, Уменьшение

Пропорции: ~70% статусов покемона чисто ложатся в графы 2-7, ~30% в
заглушку. Бланк не растёт — 8 граф на всех.

Замечания по реализации:
- "Память" статуса (нарастающий сильный яд) хранится ПОЛЕМ на покемоне
  (уже есть p.PoisonTurns). Карточка читает/двигает его в КаждыйХод.
- Движок вместо разбросанных switch делает 3-4 общих цикла: "пройди по
  статусам покемона и дёрни соответствующую графу".

--------------------------------------------------------------------
6. КАК В ЭТО ЛОЖАТСЯ УСЛОВНЫЕ АТАКИ (Отростки) — помощник условий
--------------------------------------------------------------------
Помощник условий = одна функция условиеВыполнено(контекст, условие),
отвечает да/нет про: погоду, тип цели/атакующего, HP, активную арену,
тип атаки. Один и тот же вопрос "идёт солнце?" нужен и Отросткам, и
огненным атакам, и разморозке — потому помощник общий.

Отростки в этой схеме: атака "повысить Атаку/СпАтаку" -> спрашивает
помощника "солнце?" -> да: ступеней 2, нет: 1. Само "повышение стата"
= обычная механика, условие = тонкая надстройка через помощника.

Иммунитеты типов (графа 2) — тот же помощник ("цель травяного типа?").

--------------------------------------------------------------------
7. ПЛАН ПО ФАЗАМ (двигаться маленькими шагами, каждый со сборкой)
--------------------------------------------------------------------
[Фаза 0] КАРКАС, без смены поведения:
   - объявить бланк StatusDef (8 граф) + реестр (map[statusID]StatusDef);
   - написать помощник условий (заготовка: погода/тип/HP);
   - перевести на карточки ТЕКУЩИЕ статусы, которые уже есть в коде
     (ожог, яд/сильный яд, паралич, сон, заморозка, + volatile что есть),
     сверив, что бой ведёт себя как раньше (пересборка + пара боёв).
[Фаза 1] Заполнить оставшиеся volatile на-покемоне статусы из вики
   (по одному, каждый в свою карточку).
[Фаза 2] Тонкий слой "атака->статус + условие" + помощник условий в
   бою; перевести Отростки на условие "солнце". Простая правка админки
   (выпадашка статуса + шанс + условие), БЕЗ JSON.
[Фаза 3] Полевые/арены — вторая стопка карточек (свой бланк), по мере
   надобности.
Иммунитеты по типам — маленькая карта/таблица (тип -> статусы), не if
в каждом эффекте.

8. ТЕКУЩЕЕ СОСТОЯНИЕ КОДА (справочники)
--------------------------------------------------------------------
- Ничего из плана ещё НЕ реализовано; battle.go/attacks.go/шаблон — в

- Сейчас логика статусов размазана: applyEffectByID (switch по

- ID статусов в БД (таблица statuses): 2 паралич, 3 ожог, 4 заморозка,

  15->дождь, 16->град, 17->буря (возвращают weatherChange).
- Погода id (таблица weather): 2 солнце, 3 дождь, 4 град, 5 буря.
- Статы (индекс StatStages / stat в изменениях): 1 Атака, 2 Защита,
  3 Скорость, 4 СпАтака, 5 СпЗащита, 6 Точность, 7 Ловкость.
- Категория атаки: 3 = статусная (без урона).
- Поле-счётчик сильного яда: p.PoisonTurns (уже существует).
- Таблица attack_stat_changes (attack_id, stat_id, stages, target, chance)
  — уже есть, используется для изменений статов; stages фиксированный
  (условия там выразить нельзя — это и есть ограничение).

9. ЧЕГО НЕ ДЕЛАТЬ
--------------------------------------------------------------------
- НЕ возвращать JSON-движок эффектов в админке (отвергнут, откачен).
- НЕ пытаться "сделать данными" уникальные механики — они код.
- НЕ переписывать всё разом: только по фазам, каждый шаг проверяемый.
- НЕ раздувать бланк новой графой под каждый статус: общий приём -> графа,
  похожие одиночки -> слить, экзотика -> СвойКод.
