1. ЦЕЛЬ И РЕШЕНИЯ ВЛАДЕЛЬЦА
--------------------------------------------------------------------
ЦЕЛЬ: после принятия вызова (Часть A) два игрока на одной локации ведут пошаговый
бой командами друг против друга, каждый со своего клиента, синхронизация — ПОЛЛИНГ.

РЕШЕНИЯ ВЛАДЕЛЬЦА:
  - БОЙ НАЧИНАЕТСЯ С ВЫБОРА ЛИДА: КАЖДЫЙ игрок САМ выбирает первого покемона (НЕ
    авто-первый-живой). Фаза «выбор лида» до начала боя.
  - Выбор лида — ВСЛЕПУЮ: команду соперника заранее НЕ показываем (no team preview).
  - УРОН СОХРАНЯЕТСЯ, как в обычном бою: HP/статусы/PP/обмороки пишутся в РЕАЛЬНЫЕ
    user_pokemons обеих команд (после боя лечиться надо).
  - Транспорт — HTTP-ПОЛЛИНГ (как в A); модель серверная (позже можно ws-пуш).
  - Наград/опыта НЕТ (как тренерский бой). Ловли нет.

НЕ ДЕЛАЕМ: ws; матчмейкинг/рейтинг; трейды; бой не на одной локации; зрители.

3. СЕРВЕРНАЯ МОДЕЛЬ (handlers/api/pvp.go, новый)
--------------------------------------------------------------------
Хранилище в памяти под мьютексом (как battleSessions): pvpSessions map[string]*PvpBattle,
pvpMu. Ключ battleID (newBattleID()). Внутри — BattleState (A=PlayerTeam, B=EnemyTeam)
+ обвязка PvP:
  PvpBattle{
    ID; BS *BattleState;              // A=Player..., B=Enemy...(указатель WildPokemon)
    AUserID, BUserID int; AName, BName string;
    Phase string;                      // lead_select | battling | await_replace | finished
    ALead, BLead bool;                 // выбрал ли лида
    AAction, BAction *pvpAction;       // сабмит текущего хода (move|switch|nil)
    AwaitReplaceA, AwaitReplaceB bool; // чей активный пал и ждёт замены
    Turn int; WinnerUserID int;
    Log []BattleLogEntry; LogSeq int;  // накопительный лог + курсор для клиента
    LastActivity time.Time;            // для таймаута/уборки
  }
  pvpAction{ Type string /*move|switch*/; AttackID int; UserPokemonID int }

СТОРОНА ИГРОКА: sideOf(pvp, userID) -> 'A' или 'B'. Все операции — через неё.
PERSPECTIVE: для запрашивающего ЕГО сторона = «player», сторона соперника = «enemy»
(чтобы переиспользовать клиентский рендер player+wild).

5. ЭНДПОИНТЫ (routes.go, /api/pvp/*)  — все JSON, auth по сессии
--------------------------------------------------------------------
  GET  /api/pvp/current
       -> активный PvP-бой для меня: {battle_id, phase, my_side} или {none:true}.
  GET  /api/pvp/state?battle_id=...
       -> PERSPECTIVE-состояние для меня: phase; my_team (для lead/замены: id,имя,
          hp,уровень,fainted); my_active, opp_active (публичные поля: имя,hp%,уровень,
          статус,типы); флаги whose_turn/waiting_for_opponent/await_my_replace;
          НОВЫЕ строки лога (since LogSeq-курсора, что прислал клиент); при finished —
          winner + мой результат (победа/поражение). Поллинг ~1.5с.
  POST /api/pvp/lead   {battle_id, user_pokemon_id}
       -> выбрать лида (phase lead_select). Проставить ActiveIdx (A) или EnemyActiveIdx
          + WildPokemon (B). Когда ОБА выбрали -> phase="battling", Turn=1.
  POST /api/pvp/action {battle_id, type:"move"|"switch", attack_id?, user_pokemon_id?}
       -> сабмит МОЕГО действия на текущий ход. Записать AAction/BAction. Когда ОБА
          сдали -> РАЗРЕШИТЬ ход (§6). Двойной сабмит/сабмит не в свою фазу — отклонять.
  POST /api/pvp/replace {battle_id, user_pokemon_id}
       -> выбрать замену павшему активному (phase await_replace, только для моей
          стороны, если AwaitReplace*). Когда нужные замены сделаны -> продолжить.
  POST /api/pvp/forfeit {battle_id}
       -> сдаться: соперник победил, phase finished, персист (§7).
Гарды: действия только для участника боя; только в свою фазу; user_pokemon принадлежит
игроку и в его команде/жив (для лида/замены — живой).

6. РАЗРЕШЕНИЕ ХОДА (pvpResolveTurn) — ЗЕРКАЛО processTurn ДЛЯ ДВУХ ЛЮДЕЙ
--------------------------------------------------------------------
Когда обе стороны сдали действие — РАЗРЕШИТЬ атомарно (под pvpMu):
  (6.1) Форс-состояния КАЖДОЙ стороны как в processTurn (зарядка ChargingMoveID/
        лок LockedMoveID/выжидание BideTurns/овации Encore) — если активный обязан
        повторить ход, его сабмит игнорируется в пользу форса (мигрировать ту же
        логику, что processTurn применяет к игроку — но применить к ОБЕИМ сторонам).
  (6.2) СМЕНЫ идут ПЕРВЫМИ (если чьё-то действие type=switch — сменить активного,
        применить ловушки входа applyEntryHazards его стороны), затем ходы.
  (6.3) ПОРЯДОК ходов: приоритет хода, при равенстве — Speed активного (как
        processTurn ~1732: сравнение Priority, затем скорость; учесть Trick Room,
        если уже поддержан). Определить first/second.
  (6.4) ИСПОЛНИТЬ каждый ход через ТЕ ЖЕ примитивы, что processTurn: урон —
        executeDamagingMove(bs, attacker, defender, move, weather, Turn, &log,
        sideFor(bs,defender), sideFor(bs,attacker), waterSport); статусные —
        applyEffectByID/applyStatChanges/applyHeal/handleCustomStatusMove/
        applySideMove/handlePhazeMove. attacker/defender = активные обеих сторон.
        После первого хода проверить обморок защищающегося (если пал — второй ход
        цели не проходит/по обстоятельствам, как в processTurn).
  (6.5) КОНЕЦ ХОДА: погодный чип (applyWeatherChip), отложенные (applyFutureAttacks),
        postProcessWeather, tickSideTimers, volatiles — как в processTurn, но для
        ОБЕИХ сторон.
  (6.6) ОБМОРОКИ/ПОБЕДА: если у стороны активный пал и есть живые -> AwaitReplace*
        = true, phase="await_replace" (эта сторона выбирает замену через /replace;
        другая ждёт). Если у стороны НЕТ живых -> соперник победил, phase="finished".
        Обе пали одновременно без живых -> ничья/по правилу (реши: победитель — у
        кого остались; если у обоих 0 — ничья).
  (6.7) Сбросить AAction/BAction; Turn++; накопить лог (LogSeq растёт).
РИСК-ЗОНА: многоходовые/лок/фазинг у ОБЕИХ сторон — переиспользуй ровно те же
хелперы и тот же порядок, что processTurn; НЕ переписывай их. Что не покрыл —
в «остатки» отчёта (MVP: корректный базовый бой важнее экзотики).

Переиспользовать СУЩЕСТВУЮЩИЙ рендер боя, скармливая perspective-состояние.
  - startPvpBattle(...) (game.js:3362, заглушка A) -> GET /api/pvp/current -> открыть

  - ФАЗА lead_select: показать МОЮ команду -> выбрать лида -> POST /api/pvp/lead;

  - ФАЗА battling: рендер боя (мой активный как «player», соперник как «enemy»);

    не сдал; по разрешению — проиграть НОВЫЕ строки лога (по LogSeq-курсору),
    обновить HP/статусы.
  - ФАЗА await_replace: если пал МОЙ активный — выбор замены из живых -> /api/pvp/replace;
    иначе «Соперник выбирает покемона…».
  - finished: экран победа/поражение; кнопка выйти. «Сдаться» -> /api/pvp/forfeit.
  - Поллинг state ~1.5с только пока бой открыт; аккуратно clearInterval при выходе/
    finished; курсор LogSeq чтобы не дублировать лог.
  - Ловли/поимки в PvP-UI НЕТ (тип боя не wild).

10. ПРОВЕРКА (DoD) — НУЖНЫ ДВА ИГРОКА
--------------------------------------------------------------------
  [ ] go build + go vet — зелёные;
  [ ] вызов -> принять -> ОБА попадают в фазу выбора лида; каждый выбирает СВОЕГО

  [ ] ход: оба выбирают действие -> ход разрешается ОДИНАКОВО у обоих (лог, HP,
      порядок по приоритету/скорости корректный);

  [ ] обморок активного -> эта сторона выбирает замену, другая ждёт; нет живых ->
      поражение, у соперника победа; корректный экран;
  [ ] «Сдаться» -> мгновенное поражение сдавшегося;
  [ ] ПЕРСИСТ: после боя HP/статусы/PP ОБЕИХ команд сохранены в user_pokemons
      (проверить БД/лечение); опыт НЕ начислен;
  [ ] РЕГРЕССИЯ: одиночные бои (дикий/тренер) не сломаны — общие примитивы целы;
      ловля в PvP невозможна;
  [ ] не зависает: оба клиента через поллинг сходятся в одно состояние; двойной
      сабмит/сабмит не в фазу отклоняется.
