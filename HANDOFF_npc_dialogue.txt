1. ЦЕЛЬ И ГРАНИЦЫ ПОТОКА A
--------------------------------------------------------------------
ЦЕЛЬ: игрок видит персонажей (NPC) на локации; кликает по NPC -> открывается
диалоговое окно (всплывающий док, как «Команда»/«Рюкзак»): реплика NPC + кнопки-
ответы. Ответы ведут по цепочке узлов (ветвящийся диалог) или завершают разговор.
Диалог хранится в БД и редактируется в админке. Схема сразу расширяема под
КВЕСТЫ (условия/действия), но квесты в этом потоке НЕ реализуем.

ПРИМЕР ДИАЛОГА (эталон для теста): NPC говорит «Хочешь тренировочный бой?»;
варианты: «Да, давай» (действие 'battle') и «В другой раз» (действие 'close').

ГРАНИЦА С ПОТОКОМ B: сам БОЙ и генерацию команды NPC делает поток B. В этом
потоке действие опции 'battle' доводится ТОЛЬКО до серверного сигнала
{kind:'battle', npc_id} и заглушки на клиенте (тост «бой скоро»). Поток B заменит
заглушку на реальный старт боя. Поля команды NPC в схеме/админке завести здесь
(§3, §6), но НЕ генерировать команду и НЕ трогать боевой движок.

НЕ ДЕЛАЕМ в потоке A:
  - боевой движок vs команда, ИИ-смену, условие победы (это поток B);
  - квесты: условия показа опций (condition_flag), действия give_item/set_flag/
    start_quest — только ЗАКЛАДКА полей в схеме, без логики;
  - награды/опыт (владелец: наград нет, опыт никому не начисляется).
Владелец подтвердил именно такой объём.

3. СХЕМА БД (поток A)
--------------------------------------------------------------------
Все правки — под бэкап pokemon.db.bak-before-dialogue. Новые таблицы — в срез
database.go (CREATE TABLE IF NOT EXISTS). ALTER для npc — идемпотентно (проверить
PRAGMA table_info(npc), добавлять колонку только если её нет).

(1) Расширение npc — поля команды для боя (ЗАВОДИМ здесь, использует поток B):
      ALTER TABLE npc ADD COLUMN team_mode TEXT DEFAULT 'random';  -- 'random'|'fixed'
      ALTER TABLE npc ADD COLUMN team_size INTEGER DEFAULT 6;       -- 1..6
      ALTER TABLE npc ADD COLUMN min_level INTEGER DEFAULT 5;
      ALTER TABLE npc ADD COLUMN max_level INTEGER DEFAULT 10;
    (В потоке A эти поля только редактируются в админке; команда НЕ генерируется.)

(2) Узлы диалога (реплики NPC):
      CREATE TABLE IF NOT EXISTS dialogue_nodes (
        id INTEGER PRIMARY KEY,
        npc_id INTEGER NOT NULL,
        node_key TEXT,               -- удобный ключ узла в рамках NPC (для авторинга/квестов)
        speaker_text TEXT NOT NULL,  -- что говорит NPC
        is_start INTEGER DEFAULT 0,  -- 1 = стартовый узел NPC (ровно один на NPC)
        FOREIGN KEY(npc_id) REFERENCES npc(id)
      );

(3) Опции (ответы игрока) — рёбра графа:
      CREATE TABLE IF NOT EXISTS dialogue_options (
        id INTEGER PRIMARY KEY,
        node_id INTEGER NOT NULL,    -- к какому узлу относится ответ
        sort_order INTEGER DEFAULT 0,
        option_text TEXT NOT NULL,   -- текст кнопки-ответа
        next_node_id INTEGER,        -- куда ведёт (NULL = конец после действия)
        action_type TEXT,            -- NULL | 'battle' | 'close' (позже: give_item/set_flag/start_quest)
        action_param TEXT,           -- параметр действия (на будущее, сейчас NULL)
        condition_flag TEXT,         -- НА БУДУЩЕЕ (квесты): показывать опцию при условии; сейчас NULL/игнор
        FOREIGN KEY(node_id) REFERENCES dialogue_nodes(id)
      );

Семантика разрешения опции (сервер, приоритет):
  - action_type == 'battle'  -> сигнал боя (поток B), диалог закрыть;
  - иначе next_node_id != NULL -> перейти в этот узел (продолжение цепочки);
  - иначе (action 'close' или пусто и next пуст) -> завершить диалог.

4. БЭКЕНД — PLAYER API (диалоги)
--------------------------------------------------------------------
Новый файл server/handlers/api/dialogue.go. Все ответы JSON. Auth — как в других
api-хендлерах (userID из сессии; для чтения диалога строго не обязателен, но
держи единообразно).

(A) GET /api/npc/{id}/dialogue  -> стартовый узел NPC:
    - найти dialogue_nodes: npc_id=? AND is_start=1 (первый). Если нет стартового —
      вернуть {npc_id, npc_name, node_id:0, text:"...", options:[]} (клиент покажет
      «…» + одну кнопку «Закрыть»);
    - собрать опции узла (ORDER BY sort_order, id), отдать только видимые
      (condition_flag сейчас игнорируем — все видимы);
    - ответ: {npc_id, npc_name, node_id, text, options:[{id, text}]}.

(B) POST /api/npc/dialogue/option  {option_id int}  -> разрешение выбора:
    - загрузить опцию по id (+ через node узнать npc_id); нет -> 404;
    - применить приоритет из §3:
        action=='battle' -> {kind:"battle", npc_id};      // заглушка B
        next_node_id!=NULL -> загрузить узел + его опции ->
            {kind:"node", node_id, text, options:[{id,text}]};
        иначе -> {kind:"close"}.
    - ответ всегда с полем kind ("node" | "battle" | "close").

(C) (Опц., желательно) в GetLocation добавить признак кликабельности: для каждого
    NPC отдавать has_dialogue bool (EXISTS стартового узла) ЛИБО type-строку.
    Клиент по нему подсветит/включит клик. Если проще — считать ВСЕ NPC
    кликабельными (у NPC без диалога откроется дефолтный «…»). Согласуй минимально.

Маршруты в routes.go (рядом с /api/battle/*):
    r.HandleFunc("/api/npc/{id}/dialogue", api.NpcDialogueStartHandler).Methods("GET")
    r.HandleFunc("/api/npc/dialogue/option", api.NpcDialogueOptionHandler).Methods("POST")

7. ТЕСТ-ДАННЫЕ И ПРОВЕРКА (DoD)
--------------------------------------------------------------------
Тест-данные (через админку ИЛИ python, под бэкап): взять NPC на стартовой локации;
собрать эталонный диалог:
  - узел START (is_start=1): «Привет! Хочешь тренировочный бой?»
      опция 1 «Да, давай»    -> action_type='battle'
      опция 2 «Расскажи о себе» -> next_node_id = узлу ABOUT (проверка цепочки)
      опция 3 «В другой раз»  -> action_type='close'
  - узел ABOUT: «Я тренирую покемонов уже много лет.»
      опция «Понятно» -> next_node_id = START (возврат) ИЛИ 'close'.

DoD (осн. ПК, обязателен ЖИВОЙ прогон — билд+vet это НЕ «готово»):
  [ ] go build -o server.exe ./server + go vet ./... — зелёные;
  [ ] на локации в «Персонажах» NPC кликабельны;
  [ ] клик по NPC -> открылся диалоговый док с именем NPC, репликой и кнопками;
  [ ] «Расскажи о себе» -> реплика ABOUT (цепочка узлов работает), возврат назад;
  [ ] «В другой раз» -> диалог закрылся;
  [ ] «Да, давай» -> заглушка (тост «бой скоро» / вызов startTrainerBattle-стаба),
      БЕЗ падения — точка стыка для потока B;
  [ ] смена локации закрывает открытый диалог; переходы не сломаны;
  [ ] админка: узлы/опции создаются, редактируются, удаляются; is_start
      единственный; next_node ссылается только на узлы этого NPC.
